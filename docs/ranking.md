# Многофакторное ранжирование исполнителей

Модуль `src/ranking/` упорядочивает исполнителей в каталоге (`GET /api/v1/user/specialists`) и в подборе под заказ (`GET /api/v1/order/:id/recommendations`). Константы — `ranking.constants.ts`, формулы — `ranking.math.ts` (чистые функции без обращения к базе), сбор данных из базы — `ranking.service.ts`.

## 1. Идея

Прежний порядок каталога держался на одном числе — байесовском рейтинге. Такой порядок закрепляет преимущество тех, кто уже получил много заказов: новый исполнитель без отзывов оказывается внизу и почти не получает показов, а значит и заказов, на которых мог бы набрать отзывы.

Новая модель ранжирует в две ступени:

1. **Многофакторный score.** Каждому исполнителю считается число из нескольких нормированных факторов: качество, соответствие заказу, опыт (с «авансом» для новичков), активность и штраф за текущую загрузку.
2. **Переранжирование с квотой для новичков.** Список, отсортированный по score, перестраивается так, чтобы в любом его начале доля новичков с заполненным профилем была не ниже заданной.

Первая ступень отвечает за качество подбора для заказчика, вторая — за то, чтобы новые исполнители получали видимость. Разделение сделано намеренно: одной формулой нельзя поднять новичка выше сильного опытного исполнителя, не ухудшив подбор, поэтому видимость новичкам гарантирует отдельный механизм — тот же приём, что переранжирование под заданное распределение в поиске кандидатов LinkedIn (Geyik et al., 2019).

## 2. Ступень 1 — score

Все факторы нормированы в отрезок [0, 1].

| Фактор | Смысл | Формула |
|---|---|---|
| Q — качество | репутация с поправкой на малое число отзывов | `(rating_score − 1) / 4`; без отзывов `rating_score` берётся равным априорному среднему 4,5 |
| R — соответствие | насколько исполнитель подходит под конкретный заказ | `0,5·cat + 0,35·skills + 0,15·price` (раздел 2.1); в каталоге не участвует |
| E — опыт | число n завершённых заказов как исполнитель, с убывающей отдачей | `min(1, ln(1 + n) / ln(1 + N_EXP))` |
| Ê — опыт с авансом | новичку с заполненным профилем засчитывается доля недостающего опыта | `eligible ? E + α·(1 − E) : E` |
| A — активность | давно ли исполнитель был на сайте | `exp(−d / D_ACT)`, d — дней с последнего визита; визитов нет — 0 |
| L — загрузка | сколько заказов сейчас в работе | `min(1, a / L_CAP)`, a — заказов в статусах «в работе» и «на проверке» |

```
score = w̃Q·Q + w̃R·R + w̃E·Ê + w̃A·A − wL·L
```

Положительные веса `w̃` — это исходные веса `wQ, wR, wE, wA`, делённые на их сумму, так что в сумме они всегда дают 1. В каталоге R не считается, и делится на сумму только `wQ + wE + wA`. Штраф `wL` не нормируется. Благодаря нормировке score исполнителя с идеальными факторами и без загрузки равен 1 и в каталоге, и при подборе под заказ, а значения сопоставимы между режимами.

### 2.1 Соответствие заказу R

```
cat    = 1, если категория заказа есть среди категорий исполнителя, иначе 0
skills = |навыки исполнителя ∩ навыки заказа| / |навыки заказа|;   у заказа нет навыков — skills = cat
price  = 1, если цена договорная или почасовая, или исполнитель не указал цену «от»;
         иначе B — бюджет заказа (число; у диапазона — верхняя граница, без неё — нижняя),
         P — цена «от» исполнителя:
         price = 1 при P ≤ B, иначе max(0, 1 − (P − B) / B)
R = 0,5·cat + 0,35·skills + 0,15·price
```

### 2.2 Константы

| Константа | Значение | Обоснование |
|---|---|---|
| wQ | 0,60 | качество — главный сигнал для заказчика, поэтому самый большой вес; со стартовыми 0,4 потеря качества подбора в одном из наборов эксперимента превышала 2% |
| wR | 0,25 | соответствие заказу — второй по важности, считается только при подборе под заказ |
| wE | 0,20 | опыт важен, но меньше качества: опыт без хороших оценок мало что значит |
| wA | 0,05 | вспомогательный фактор; его польза (исполнитель на связи) в имитационной модели не измеряется, поэтому вес минимальный |
| wL | 0,10 | ровно столько, чтобы свободный исполнитель обходил занятого при близком score |
| N_EXP | 30 | при 30 завершённых заказах опыт достигает 1, дальше преимущество не растёт |
| α | 0,5 | исполнитель с заполненным профилем получает половину недостающего опыта; при 0,75 качество подбора падает больше чем на 2% (в среднем на 2,2%) |
| D_ACT | 14 дней | за две недели без визитов активность падает в e раз (≈ 0,37) |
| L_CAP | 3 | больше трёх заказов параллельно — перегрузка, штраф максимален |
| p (NEWCOMER_SHARE) | 0,2 | не меньше одного новичка на каждые пять мест выдачи; при 0,3 в худшем наборе эксперимента качество выбранных исполнителей падает на 2,6% |
| N_NEW | 5 | после пяти завершённых заказов рейтинг уже информативен — исполнитель перестаёт быть новичком |
| PRIOR_MEAN | 4,5 | априорное среднее байесовского рейтинга, то же, что в модуле отзывов |
| веса R | 0,5 / 0,35 / 0,15 | категория — главный признак, навыки её уточняют, о цене обычно договариваются в чате |

Веса, α и p выбраны имитационным экспериментом (`docs/experiment/results.md`, команда `npm run experiment:ranking`) по одному критерию: максимум доступа новичков (доли новичков, получивших первый заказ) при условии, что механизмы для новичков снижают истинное качество подбора не больше чем на 2% **в каждом** из шести наборов случайных данных, а не только в среднем.

- **Веса.** Стартовые значения были wQ = 0,40, wA = 0,10, остальные те же. С ними на одном из наборов качество выбранных исполнителей падало на 3,0%, поэтому они отсеялись. С финальными весами потеря не хуже −1,5% во всех наборах.
- **p.** Тот же критерий, что и для весов. p = 0,2 — наибольшая квота, прошедшая его. p = 0,3 — граница компромисса: первый заказ получают все новички, но в худшем наборе качество выбранных падает на 2,6%. При этом 100% — эффект насыщения модели (около 130 новичков на 2000 заказов без притока новых), а не реалистичная оценка.
- **α.** Среди точек, прошедших критерий, α = 0,5 даёт максимум доступа; α = 0,75 не проходит ни при каком p.

С финальными параметрами хотя бы один заказ за симуляцию получают в среднем 85% новичков (в прежнем порядке — 14%), а механизмы для новичков снижают истинное качество подбора в среднем на 0,6%.

### 2.3 Почему так

- **Опыт через логарифм с потолком.** 5 и 30 заказов различаются заметно, а 50 и 200 — уже нет. Логарифм ограничивает преимущество опыта среди опытных исполнителей; доступ новичков обеспечивают аванс опыта и квота (ступень 2). Сам по себе логарифм концентрацию заказов почти не снижает: в эксперименте коэффициент Джини по заказам 0,934 в прежнем порядке и 0,927 без механизмов для новичков.
- **Аванс опыта как доля недостающего опыта**, а не отдельный бонус. Отдельный бонус, гаснущий быстрее, чем растёт опыт, создаёт «яму»: исполнитель с 3–10 заказами оказывается ниже совсем нового. Ê не убывает с ростом n при любом α из [0, 1), поэтому исполнитель, выполнив новый заказ, никогда не опустится ниже, чем был сам до этого при прочих равных. Аванс уменьшается по мере накопления данных об исполнителе — по сути это бонус за исследование малоизвестного варианта, как в алгоритме UCB1 (Auer et al., 2002).
- **Штраф за загрузку.** Если у сильного исполнителя три заказа в работе, следующий заказчик увидит выше свободного исполнителя — заказы распределяются шире, а заказчик быстрее получает результат.
- **Качество Q не меняется.** Байесовское среднее уже решает проблему «одна пятёрка лучше ста оценок 4,9» (Miller, 2009). Исполнителю без отзывов Q считается по априорному среднему 4,5 — это значение той же байесовской формулы при нуле отзывов. Эксперимент показал, что 4,5 выше средней оценки по платформе (в модели ≈ 4,0) и завышает рейтинг исполнителей с 1–3 отзывами в среднем на 0,34 балла; правильнее брать априорным средним среднюю оценку платформы (направление развития, раздел 8).

## 3. Кто считается новичком

**Заполненный профиль (eligible)** — защита от фейковых аккаунтов: аванс опыта и место по квоте получает только тот, кто заполнил профиль. Это аналог требования Upwork о 100% заполненном профиле для статуса Rising Talent. Должны выполняться все условия сразу:

- есть аватар;
- описание не короче 80 символов;
- указана специальность;
- выбраны хотя бы 1 категория услуг и хотя бы 3 навыка;
- указана цена «от»;
- если исполнитель работает на месте или в обоих форматах — указан город;
- почта подтверждена.

Функция `isEligible` возвращает и список невыполненных условий (`missing`) — по нему интерфейс может подсказать исполнителю, что заполнить.

**Новичок** — eligible и меньше N_NEW = 5 завершённых заказов как исполнитель.

## 4. Ступень 2 — квота для новичков

После сортировки по score итоговый список собирается по позициям k = 1, 2, …:

1. Требуемое число новичков на позиции k — `⌊p·k⌋`.
2. Если уже поставлено меньше — на позицию k ставится лучший по score из оставшихся новичков (место **по квоте**).
3. Иначе — лучший по score из всех оставшихся.
4. Когда новички закончились — дальше обычный порядок.

Свойства алгоритма:

- в любом начале выдачи длины k новичков не меньше `⌊p·k⌋`, пока они есть (при p = 0,2 новичок гарантированно есть к 5-й позиции, двое — к 10-й);
- новичок, поднявшийся сам за счёт высокого score, засчитывается в квоту — квота добавляет места только тогда, когда новичков в выдаче не хватает;
- места по квоте достаются лучшим новичкам, а не случайным; порядок внутри групп «новички» и «остальные» сохраняется;
- при p = 0 или без новичков результат совпадает с обычной сортировкой по score.

**Пример на 10 позициях.** Восемь опытных исполнителей со score 0,90; 0,85; …; 0,55 и два новичка со score 0,20 и 0,10.

| Позиция k | ⌊0,2·k⌋ | Новичков до позиции | Кто встаёт | По квоте |
|---|---|---|---|---|
| 1–4 | 0 | 0 | опытные 0,90 … 0,75 | — |
| 5 | 1 | 0 | новичок 0,20 | да |
| 6–9 | 1 | 1 | опытные 0,70 … 0,55 | — |
| 10 | 2 | 1 | новичок 0,10 | да |

Без квоты оба новичка оказались бы на 9-й и 10-й позициях.

## 7. Как включить через API

```
GET /api/v1/user/specialists                              — новый порядок (rankMode=weighted по умолчанию)
GET /api/v1/user/specialists?rankMode=legacy              — прежний порядок, для сравнения
GET /api/v1/user/specialists?rankMode=weighted&explain=1  — с разбором score
```

С `explain=1` у каждого исполнителя появляется поле:

```json
"ranking": {
  "mode": "weighted",
  "score": 0.832,
  "position": 5,
  "quotaSlot": true,
  "factors": { "Q": 0.91, "E": 0.20, "Eadv": 0.60, "A": 1.0, "L": 0 },
  "isNewcomer": true,
  "missing": []
}
```

`quotaSlot: true` — место выдано по квоте (без квоты здесь стоял бы другой исполнитель). `missing` — невыполненные условия заполненного профиля. В режиме `legacy` с `explain=1` порядок прежний, `position` — позиция в прежней выдаче, а `score` и `factors` показывают, как того же исполнителя оценила бы новая модель. Остальные фильтры каталога (поиск, категории, формат, город) работают в обоих режимах одинаково.

### Подбор под заказ

```
GET /api/v1/order/:id/recommendations?limit=10&explain=1
```

Только автору заказа (чужому — 403) и только для опубликованного заказа в статусе `active`, иначе пустой список. `limit` — от 1 до 20, по умолчанию 10. Кандидаты: принимают заказы, не автор, формат совместим (заказ на месте — исполнители «на месте» или «оба» из того же города; удалённый — «удалённо» или «оба»), есть категория заказа или хотя бы один его навык. Порядок — обе ступени, score с R. Ответ — массив карточек исполнителей с полями `isNewcomer` и `alreadyResponded` (уже откликался на этот заказ); с `explain=1` — ещё `ranking`, в котором кроме полей выше есть `contributions` — вклад каждого фактора в score (`w̃·фактор`, у L со знаком минус, сумма равна `score`).

## 8. Ограничения

- Score и квота считаются в памяти по всем кандидатам, прошедшим фильтры, и только потом выдача делится на страницы. Это нормально до нескольких тысяч исполнителей. Дальше — хранимое поле score с пересчётом по событиям (новый отзыв, завершение заказа, визит) и квота поверх выборки из индекса.
- Априорное среднее 4,5 в байесовском рейтинге выше средней оценки по платформе, поэтому рейтинг исполнителей с 1–3 отзывами завышен. В прежнем порядке исполнитель без отзывов (`rating_score = 0`) стоит в самом конце выдачи, а исполнитель с одной-двумя хорошими оценками — часто выше опытных. Брать априорным средним среднюю оценку платформы — направление развития; код рейтинга в работе не менялся.
- Квота работает в пределах одной выдачи и не учитывает, сколько показов исполнитель уже получил раньше. Учёт накопленной видимости (Biega et al., 2018) — направление развития.
- Активность считается по полю «последний визит», которое обновляется при загрузке собственного профиля (`GET /user/me`) и при входе в чат и выходе из него, а не при каждом действии на сайте.
